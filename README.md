# Devices API

A Devices Management application.

## Built with 
**Spring Boot 4**, **Java 25**, **PostgreSQL**, **Redis**, **Flyway**, **JPA**, **MapStruct**, and **Lombok**.

## Features

- Create a new device
- Fully or partially update an existing device
- Fetch a single device
- Fetch all devices
- Fetch devices by brand and/or state
- Delete a single device

## App Amenities/Services
- 10 default cellular/eSIM-oriented devices
- Swagger / OpenAPI documentation
- Redis caching for hot reads
- Command-first asynchronous write processing over Kafka
- DB change management and migration with Flyway
- DB CRUD management with Spring JPA
- Structured JSON logs with correlation IDs
- Dockerized runtime


## Domain Rules

- `createdAt` is immutable and generated by the server
- `name` and `brand` cannot be changed while a device is `IN_USE`
- devices in `IN_USE` state cannot be deleted

## Technology/Architectural Choices

- **Architecture**: microservice with DDD-style packaging
- **API**: REST with controller interfaces + impls
- **Async model**: Spring MVC + Java 25 virtual threads
- **Persistence**: PostgreSQL + Spring Data JPA
- **Caching**: Redis
- **Event-driven architecture**: command-first asynchronous publish commands by kafka

## Run locally with Docker Compose

```bash
cd /devices-api

docker compose up -d
```

Console logging is plain text by default so exceptions are easier to read.

To enable structured JSON console logs, run with the `structured-logs` profile:

```bash
SPRING_PROFILES_ACTIVE=structured-logs docker compose up --build
```

Accessing Application:

- Swagger UI: `http://localhost:8080/swagger-ui.html`
- OpenAPI JSON: `http://localhost:8080/api-docs`
- Health: `http://localhost:8080/actuator/health`


## Example API usage

### Create device

```bash
curl -X POST http://localhost:8080/api/v1/devices \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "eSIM Gateway X1",
    "brand": "Motorola",
    "state": "AVAILABLE"
  }'

# returns 202 Accepted with command metadata and the generated deviceId
```

### Get all devices

```bash
curl http://localhost:8080/api/v1/devices
```

### Filter by brand

```bash
curl 'http://localhost:8080/api/v1/devices?brand=Motorola'
```

### Filter by state

```bash
curl 'http://localhost:8080/api/v1/devices?state=IN_USE'
```

### Replace a device

```bash
curl -X PUT http://localhost:8080/api/v1/devices/{id} \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "5G Edge Router X2",
    "brand": "Nokia",
    "state": "IN_USE"
  }'

# returns 202 Accepted and processes the replacement asynchronously
```

### Patch a device

```bash
curl -X PATCH http://localhost:8080/api/v1/devices/{id} \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "INACTIVE"
  }'

# returns 202 Accepted and processes the update asynchronously
```

### Delete a device

```bash
curl -X DELETE http://localhost:8080/api/v1/devices/{id}

# returns 202 Accepted and deletes asynchronously if business rules allow it
```

## Kafka command flow

API endpoint invocations do not write directly to the database. Instead, the application follows a command-first, asynchronous processing model, where CRUD events are published and subsequently consumed by the same service. This approach allows the API to release resources as quickly as possible while the database operation is processed asynchronously.

Current flow:

```text
HTTP request
   ↓
Controller/service
   ↓
Validate business rules
   ↓
Publish Kafka command
   ↓
Return 202 Accepted
   ↓
Same-service (different pod) Kafka consumer
   ↓
Persist to PostgreSQL (Redis When reading not writing)
```

Published command event types:
- `DEVICE_CREATE_REQUESTED`
- `DEVICE_REPLACE_REQUESTED`
- `DEVICE_UPDATE_REQUESTED`
- `DEVICE_DELETE_REQUESTED`


Local broker/topic details:
- Broker: Kafka-compatible single-node Redpanda in `docker-compose.yml`
- External broker address from host: `localhost:19092`
- Internal broker address from app container: `kafka:9092`
- Topic: `devices.commands.v1`

## Testing

Run all tests:

```bash
cd devices-api
mvn test
```
Run the optional PostgreSQL container integration tests:
```bash
cd devices-api
mvn -Ppostgres-it verify
```

The `postgres-it` profile runs only `*PostgresIT` tests and validates:

- Flyway migration compatibility with real PostgreSQL
- JPA mappings and repository queries against PostgreSQL
